# Assumptions

| # | What was unclear | What you assumed | Why |
|---|---|---|---|
| 1 | `filers.csv`'s given CIKs are described as "not all trustworthy." | Verified all 20 against SEC's `cik-lookup-data.txt` and EDGAR company search. 17 were correct as given. 2 were genuinely wrong (Tudor Investment Corp: 854157→923093; Situational Awareness LP: 1697748→2045724). One (The Baupost Group LLC) initially looked wrong because the closest fuzzy name match in the lookup file, CIK 1054420 ("Baupost Group LLC /ADV"), stopped filing 13Fs in 2002 — but the *given* CIK 1061768 ("Baupost Group LLC/MA") is the currently active filer, so it was left as `given`. | Name-based fuzzy matching alone is unreliable when two similarly-named entities exist (one active, one dormant). Verifying against which CIK is *currently filing* was more reliable than which name matched more closely. |
| 2 | Chapter 1's example shows one cached file per filing (`{accession}.xml`), but `filings.parquet`'s schema requires several cover-page-only fields (`filing_manager`, `crd_number`, `form_13f_file_number`, `table_entry_total`, etc.) that do not exist in the information table document. | Cache **both** documents per filing: `{accession}.xml` for the information table (or the cover page alone, for notices) and `{accession}_cover.xml` for the cover page. | Chapter 3 cannot produce a schema-conformant `filings.parquet` from the information table alone. Caching both up front avoids re-fetching from EDGAR during Chapter 3. |
| 3 | The information table's namespace prefix is inconsistent across filers (no prefix, `ns1:`, `n1:` — confirmed by direct inspection in `submission/eda.py`, section 1). | Parse every XML element by namespace-stripped local tag name (`local_name()`), never by literal tag string. | A parser keyed on a literal tag name silently returns zero rows for whichever prefix style it wasn't written against — this isn't a minor formatting quirk, it's a correctness bug waiting to happen. |
| 4 | Schema says `cusip` is not unique within a filing, but doesn't say why. | Investigated directly (`submission/eda.py`, section 3): AQR's Q1 2026 filing has 17,093 duplicate CUSIP rows out of 20,832. Inspecting one repeated CUSIP shows each row has a different `value` and `otherManager` reference — consistent with a large multi-strategy platform reporting each internal sub-manager's position on the same security separately. Treated every row as a distinct, legitimate holding; never deduplicated on `cusip` or any column combination. | Confirmed with evidence rather than assumed — the alternative (deduplicating) would have silently discarded genuine data. |
| 5 | `is_amendment`, `amendment_no`, `amendment_type` — how to populate these when none of the 40 in-scope filings are amendments. | Derived `is_amendment` from `form_type.endswith("/A")` (a live computation, not a hardcoded constant) and looked for `amendmentNo`/`amendmentType` elements in the cover page, defaulting to `None` when absent. All 40 filings in scope are original filings, so these are `False`/`null` across the board — a fact about this dataset, not a shortcut in the code. | Keeping the logic general (rather than hardcoding `False`) means it would behave correctly if the roster or scope changed to include an actual amendment. |
| 6 | Chapter 4's agent needs an LLM endpoint; the grading environment (vLLM + Gemma-31B, with `guided_json` support) is not available for local development. | Developed and tested against a local Ollama instance running `llama3.2:3b`, which does not support `guided_json`. This surfaced two real, worth-fixing issues that a guided-decoding server structurally cannot produce, but a well-behaved agent should tolerate anyway: (a) JSON occasionally wrapped in markdown code fences, (b) an `action` value outside our fixed enum. Added defensive handling for both (fence-stripping before `json.loads`, and fuzzy-matching an out-of-enum action back to the nearest valid one via `difflib`). | Even though vLLM's guided decoding makes these specific failure modes structurally impossible at grading time, defensive parsing of model output is exactly what 04-serve.md asks for ("model output is untrusted input"), and it costs nothing to keep. |
| 7 | With only a 3B-parameter local model available for development (vs. the 31B-parameter Gemma used for grading), most of the example questions in `docs/questions-examples.md` return `null` locally — not because the query-execution logic is wrong, but because the small model frequently misclassifies the intent or fills hints with the literal string `"null"` instead of a real value or true JSON null. | Verified the query-execution logic (`_execute`) directly, bypassing the LLM entirely, by hand-constructing intents for four of the example questions and checking the results against the raw data (e.g. Renaissance Technologies' Q2 2026 distinct-issuer count matched the cover page's own `tableEntryTotal` of 3140 exactly). Also added handling for the literal string `"null"` in hint fields, since a larger model could plausibly produce this too. | Given no access to the grading model, this was the most defensible way to build confidence in correctness: separate "does the query engine give the right answer for a given intent" (fully testable) from "does the LLM extract the right intent" (only testable at grading time). |
